# publish-skill 首轮 E1 审计

## 总体判断

`publish-skill` 应该保留，核心流程不建议瘦身。

它最值钱的不是教模型如何调用一个发布命令，而是把外部写操作拆成授权、预检、创建、反查和部分失败状态，并在删除前同时要求人的逐次确认与代码中的标题核对。

入口文件约 4.4KB，职责边界清楚，和 `title-skill` 的默认加载偏重不是同一类问题。当前适合分层的是平台错误码、构建产物等时效或环境资产，不是权限与验收规则。

## 审计上下文

- 模型：GPT-5
- 精确版本：未知
- 证据等级：E1，只读结构、代码与测试审计
- 真实发布任务：0
- 无 Skill 对照：未执行
- 置信度：低

本轮没有读取 `.env` 内容，也没有调用任何真实发布接口。

## 资产构成

本次拆出 12 个规则块：

- 通用动作 `generic`：0
- 一次性或时效资产 `temporary`：2
- 独家经验 `proprietary`：8
- 混合资产 `mixed`：1
- 证据不足 `unknown`：1

比例只表示本次规则块构成，不代表科学精度。

## 最值得保留

1. 只读检查与创建草稿的授权分界。
2. `release-manifest.json`、文件 SHA 与多个标题来源的逐字核对。
3. 创建后反查：只有 `ok=true`、存在 `media_id` 且标题验证成功才算完成。
4. 删除前的人类逐次确认，以及代码里的完整标题二次核对。
5. `created=true` 但反查失败等部分成功状态，避免错误回执。
6. 微信列表空白、Prompt 换行和 URL 编码图片路径等真实平台失败记录。
7. 远程图片下载对本地、私网和异常端口的网络限制。

这些规则保存的是权限、事实和真实事故，不是模型升级后就会失效的操作教程。

## 可以单独维护

平台错误码和字段上限属于时效资产。它们仍有价值，但生命周期与授权规则不同，应该独立更新和验证，避免“某条错误码过时”等同于“整个 Skill 过时”。

仓库根目录还存在一个约 9.7MB 的 Mach-O 可执行文件。它是构建产物，不是 Skill 规则。是否移出版本库取决于是否有外部分发流程依赖，本轮只能交给人工判断。

## 测试结果

实际运行 `go test ./...`，所有 Go 测试通过。覆盖范围包括：

- 发布前本地阻断条件。
- manifest、SHA 与标题漂移。
- 列表分页与空草稿箱。
- 删除标题不匹配时拒绝执行。
- 图片 URL 的本地和私网限制。
- 上传重试与最终失败。
- HTML 列表空白和 Prompt 换行。

这些测试证明现有代码约束在当前仓库里能执行，但不能证明模型脱离 Skill 后仍会遵守，所以模型替代证据仍然只有 E1。

## 对 sieve-skill 暴露的新问题

1. 当前资产类型只描述规则价值，无法准确表达“源代码、测试、构建产物、秘密文件”这些仓库角色。
2. E1/E2/E3 只描述模型替代证据，没有单独表达“代码行为已经由测试验证”。
3. 清单工具会列出 `.env`，虽然没有读取内容，但应该显式识别为敏感文件并禁止后续加载。
4. 仅看入口引用无法发现外部调用方，给出 `externalize` 前还需要依赖关系检查。

## 需要人决定

3. 是否进行无 Skill 发布模拟，验证模型能否自行守住授权和反查顺序。
